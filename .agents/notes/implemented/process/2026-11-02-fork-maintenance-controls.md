# Agent Note: Fork maintenance controls

Status: implemented

English | [中文](2026-11-02-fork-maintenance-controls.zh.md)

## Problem

The Tricade fork has no protection for `main`. Its inherited Dependabot configuration checks only GitHub Actions, while vulnerability alerts and security updates are disabled. The pnpm workspace contains version-specific patches that need individual compatibility review.

## Decision

Require pull requests, signed commits and resolved conversations on `main`, including for administrators. Reject force pushes and deletion. Require no outside approval because the fork has a single maintainer; use only CI contexts actually emitted by this fork. The owner explicitly authorized these fork-local controls in the task conversation.

Check npm workspace dependencies and GitHub Actions weekly, with bounded open pull requests. Group ordinary minor and patch updates, leaving patched packages and Electron in individual pull requests. Do not ignore their updates or enable automatic merging. Keep `pnpm-workspace.yaml` patches and overrides authoritative.

Enable vulnerability alerts and Dependabot security updates. GitHub's current [pnpm support documentation](https://docs.github.com/en/code-security/reference/supply-chain-security/supported-ecosystems-and-repositories#pnpm) states that version updates support pnpm 12, but its two-document lockfile is not recognized by the dependency graph. This repository pins pnpm 12.6.0 and uses that format. A default-branch SBOM exported after the security merge contained only 233 package records and omitted known transitive dependencies, despite GitHub marking the earlier 54 alerts fixed. That status is not evidence of complete coverage.

Preserve the working lockfile and use the pinned package manager's native `pnpm sbom --lockfile-only --sbom-format cyclonedx` export. Adapt its [CycloneDX 1.7](https://cyclonedx.org/docs/1.7/json/) project graph to the [GitHub dependency-submission API](https://docs.github.com/en/rest/dependency-graph/dependency-submission?apiVersion=2026-03-10). Retain every exported package and dependency edge, including platform-specific optional dependencies, with original package URLs and versions. Reject empty inventories, missing package URLs, missing graph records and unresolved references. Exclude the application root itself; merge peer-context edges only when GitHub's PURL identity combines their packages. Do not guess runtime/development scopes or encode patches as new versions.

Generate the snapshot on PRs, main pushes and manual runs in a read-only job without installing application dependencies or running their scripts. Only a separate job for a main push or main manual run receives `contents: write`; it downloads that run's artifact, executes no checked-out application code, verifies the SHA/ref and current main head, and submits to GitHub. Keep one stable detector/correlator and require an accepted or successful API result. The native export covers the application/workspace graph, not the separate pnpm bootstrap executable graph or system toolchain. Only GitHub readback can establish that a submitted graph was indexed.

Serialize runs per ref without canceling an in-flight submission. A main change after the SHA guard can briefly leave the older graph visible until the queued newer run submits; failed generation or submission is never passing evidence. Retain the native SBOM artifact as provenance: pnpm represents the two MLX codeload dependencies with package-version PURLs, while their distribution URLs and hashes remain in the SBOM rather than the submitted PURL graph.

Run the existing CI workflow on pushes to every branch using `branches: ["**"]`, while retaining its PR triggers, jobs, permissions and affected-check planner. The repository's Actions setting was enabled while the individual CI workflow was `disabled_fork`; enabling that workflow restored automatic PR and push runs. A successful manual baseline run does not satisfy required PR checks under GitHub's current [event eligibility rules](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks#checks-from-some-workflow-jobs-are-not-evaluated); `push` is eligible. This supplies a regular event path for feature, security, Dependabot and upstream-sync branches. The [branch-only filter](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onpushbranchestagsbranches-ignoretags-ignore) excludes tags.

Feishu failure-notification setup and delivery run only when both webhook credentials are configured. A first step checks its secret environment and exposes only an `enabled` boolean; later setup steps receive neither credential. The send step retains its own secret environment. Missing credentials skip notification work without masking failed validation jobs. This follows GitHub's [step condition and secret context rules](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#jobsjob_idstepsif).

The macOS platform job uses the standard `macos-26-intel` runner. Two successive full CI runs could not acquire `macos-latest` runners; both ended with GitHub's explicit macOS arm64 capacity annotation before executing any steps. On 2026-11-02, the [official runner table](https://docs.github.com/en/actions/reference/runners/github-hosted-runners) maps `macos-latest` to macOS 26 arm64 and lists `macos-26-intel` as a standard macOS 26 x64 runner. This preserves the OS major and the unchanged `pnpm check --group platform` selection. The selected native smoke tests accept both Darwin architectures. Intel execution does not prove Apple-Silicon binary or ABI compatibility; that remains separate release verification. Do not treat unavailable runners as successful checks or suppress the platform gate.

## Alternatives considered

Requiring another maintainer's approval would prevent a solo owner from merging their own work. Requiring guessed CI names would leave every PR blocked. Ignoring patched packages would conceal available updates; grouping them into routine updates would hide their patch-rebase work. Changing the lockfile format solely to accommodate GitHub would change a working package-manager contract outside this task. The reviewed Component Detection parser reads one YAML document; a native pnpm export avoids another lockfile parser. The reviewed SPDX submission action includes the application root as a dependency and only logs some unsuccessful API results; the small CycloneDX adapter preserves the native export and fails explicitly. Disabling required checks or substituting a manual dispatch for an eligible event would defeat the intended merge gate.

## Consequences

Dependabot may need manual help rebasing version-specific patches. Required checks must be updated if CI job names change. Upstream synchronization now needs a pull request. Submitted upstream versions can reopen vulnerability alerts for locally patched packages; preserve those warnings and their remediation evidence rather than dismissing them or disguising versions. The native SBOM does not describe local patch contents, pnpm bootstrap binaries, or the installed machine's toolchain. Branch pushes and PR events can produce separate CI runs when both triggers are delivered; the fork accepts that extra runner work for the additional eligible event path. Existing PR-only policy steps remain PR-only; push checks do not prove those steps ran.
